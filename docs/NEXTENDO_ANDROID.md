# Nextendo Network integration — Android

- Registered redirect URI: `com.nex.nx://oauth/callback`
- Requested scopes: `identity friends presence profil game.matchmaking`

This is the NEX application's public identity, not a player token and not a client secret. NEX is a public Android OAuth client and must use Authorization Code + PKCE (S256). Never embed a client secret in the APK.

## Android OAuth endpoints

Use the Android integration endpoints documented by Nextendo:

- Authorization: `https://nextendo.network/api/oauth/authorize`
- Token exchange and refresh: `https://nextendo.network/api/oauth/token`
- Game-token endpoint: `https://nextendo.network/api/nex-token`

The portal-generated authorization URL is an example/template. Replace its placeholder challenge with a new PKCE challenge generated by NEX for each authorization attempt. Construct the URL with a URI builder; do not concatenate unescaped query parameters.

## Sign-in sequence

1. Generate a cryptographically random PKCE `code_verifier` with 43–128 URL-safe characters, a SHA-256 `code_challenge` encoded as Base64URL without padding, and a random `state`.
2. Keep the verifier and state in a short-lived, lifecycle-safe pending-auth transaction.
3. Open the authorization URI in a Chrome Custom Tab or system browser. Never collect a Nextendo password inside NEX.
4. Receive the callback through the registered Android deep link `com.nex.nx://oauth/callback`.
5. Compare the returned `state` with the pending state. Reject missing or mismatched values and OAuth error callbacks.
6. Exchange the one-time code at `/api/oauth/token` using `grant_type=authorization_code`, the same `client_id`, the exact `redirect_uri`, and the original `code_verifier`.
7. Save the access and refresh tokens immediately in encrypted storage backed by Android Keystore. Never log tokens or include them in URLs.
8. Refresh with `grant_type=refresh_token` when required. Refresh tokens rotate; persist the new refresh token immediately.

The access token is used for account API calls within the scopes the player approved. The refresh token is used only to renew the session. Token values must never be added to crash reports or analytics.

## Account profile, friends and presence

After OAuth succeeds, implement each API according to the current Nextendo API contract and the scopes the player granted:

- `identity`: base player identity, PID, username, Friend Code and avatar.
- `friends`: the player's authorized friend list and friend data.
- `presence`: read presence and publish the current app/game activity using the documented presence endpoint and heartbeat requirements.
- `profil`: read and edit the player's profile fields supported by the API.
- `game.matchmaking`: access the game-token flow and matchmaking-related capabilities.

Do not infer API paths or response fields from the scope names alone. Add typed response models and API tests against the live developer documentation before wiring profile/friends/presence screens.

## Account token vs game token

These credentials are not interchangeable:

- OAuth `access_token`: account API access (identity, friends, presence and profile).
- OAuth `refresh_token`: renews the account session; rotation must be handled.
- NEX game token (`nex_token`, with the `nx2.` token format): obtained from `GET /api/nex-token` using the OAuth bearer token. The response also includes player identity data and expiry.

The game token lasts 24 hours according to the Nextendo developer guide. Fetch a new one at game launch or when it expires and keep its expiry separate from OAuth token expiry. Never put an OAuth access token or bare PID in a game's `nnex` claim.

## In-game authentication still required

A successful OAuth login proves only that the user authorized the NEX application. It does not prove that a game can log in.

The emulator's ACC/BAAS path must construct the game's identity token using the NEX account PID and fresh Nextendo `nex_token` in the `nnex` claim, following the current Nextendo/Ryujinx reference implementation. The gateway also enforces its current application identity / client attestation rules. Any signing key, application token, attestation, request header or release proof required by the gateway must be provisioned specifically for NEX by the Nextendo application owner/operator; never copy another developer's private material.

A valid `nex_token` alone is not enough: online play also depends on correct ACC/BAAS serialization/signing, DNS redirection, TLS/SNI behavior, game-specific NEX services, matchmaking and NAT/P2P networking. The NEX project must not claim in-game multiplayer support until a real supported-title session has passed testing.

## Android callback manifest contract

Register an exported callback activity (or equivalent deep-link handler) with an intent filter for:

- scheme: `com.nex.nx`
- host: `oauth`
- path: `/callback`

Validate state inside the application before exchanging the code. Do not treat a deep-link callback as authenticated merely because it was opened.
